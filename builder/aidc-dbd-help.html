Install and update

AIDC DBD installs with AIDC-DBD-Setup-<version>.exe. It needs Windows 10 or 11, 64-bit.

Install

  1. Check the download against the release's SHA-256 (optional, recommended): 
    Get-FileHash "$env:USERPROFILE\Downloads\AIDC-DBD-Setup-<version>.exe" -Algorithm SHA256
  2. Run AIDC-DBD-Setup-<version>.exe. The installer is unsigned, so Windows SmartScreen may show "Windows protected your PC": click More info, then Run anyway.
  3. Choose Only for me: it needs no administrator rights. (Anyone who uses this computer installs for every user and asks for administrator rights.)
  4. Keep the suggested folder (for Only for me, %LOCALAPPDATA%\Programs\AIDC DBD) or choose another, then Install.
  5. The installer adds an AIDC DBD shortcut on the desktop and in the Start menu. Start the app from either.
  6. Check Help > About AIDC DBD: it shows the app version, the builder version and the builder's SHA-256.

Update

  1. Save your design and close AIDC DBD, including any DC Layout Builder windows. A running window keeps the version it was started with.
  2. Run the new AIDC-DBD-Setup-<version>.exe. It replaces the installed version in the same folder; the shortcuts keep working.
  3. Check Help > About AIDC DBD.
Keep each release's Setup file: it is your copy of that version. To go back, close the app and run the older Setup file.

Uninstall

Windows Settings > Apps > Installed apps > AIDC DBD > Uninstall. Your project folders are not touched.

Portable zip (where installing is not allowed)

Each release also has AIDC-DBD-<version>-win-x64-portable.zip. Unzip it into a folder of its own and run AIDC DBD.exe from that folder; for a shortcut, right-click the .exe > Send to > Desktop (create shortcut).

Do not copy AIDC DBD.exe out of its folder: it needs the resources folder, the DLLs and the other files beside it.

Load the input sheet

The input sheet sets the design in one step from the customer's values.

  1. File > Input sheet template (blank) saves the template, generated from the builder's catalog. Input sheet filled from this design saves one filled from the open design. In a browser, File ▾ > Input sheet on the toolbar does the same.
  2. The customer fills it in. The app reads .xlsx or a CSV with the columns key,value,unit,source. It does not read .txt.
  3. File > Load input sheet… reads it. A meter shows each step: reading the file, reading the sheet, applying the settings, building the design, drawing, checking the result. If a step fails, the status line names it and the open design is put back.
  4. The import report lists every row. Download session input file saves the record; it is also saved to the project folder.

Import report statuses

StatusMeaning

Fabric Designer

The main window. It holds the design: you set the site and platforms, build from the rack count, and every view, check and output is generated from that one model. It opens when the app starts.

Build the design

  1. Set Customer and Code, the Fabric platform, the back-end planes and platform, and the front end, or load the input sheet.
  2. Enter Total racks and click the green Build from rack count.
  3. Open Fabric health and clear every Error (see Read the health verdict).
  4. Save writes the design file; Load opens one.
After you change a setting that changes the design (platform, planes, switches, pod size), click Build from rack count again. When the rack box and the canvas disagree, the status line says "box says N, model has M — click Build".

Storage on rack-scale platforms (NVL72) is sized per scalable unit, the platform's 8-rack unit.

Tenants

A tenant is one isolated customer or workload on the site's front end. Enter the count in the Tenants box (1 for a single-tenant site), then assign hosts with the Tenants button.

Each tenant getsWhere
Its own VRF and VXLAN VNIFront-end leaves and spines
Its own routing instance (Junos SRX) or virtual router (Cisco FTD)Edge firewalls
Its own DPU (HBN) configuration; the spines' route-target filters admit only its routesEach of its hosts' BlueField DPUs
Its own VIPs and SNAT poolF5 BNK ingress
  • Limits: one edge block (a firewall pair) holds 120 tenants. Past 120, or when N-S Gbps needs more firewall capacity, the builder adds edge blocks, up to 15 blocks and 989 tenants. F5 BNK's per-tenant limits and the VIP block can lower the site's ceiling.
  • Past 120 tenants the route distinguishers move to compact ranges; nothing to set.
  • The input sheet row is fe.tenants.

Gates

  • Release gate: the site runner refuses a design exported from a different builder file (its SHA-256 differs). Export the site-runner file again from this release.
  • Fingerprint gate: the site runner and the Layout service rebuild the design from its settings and refuse unless it matches the window's. A mismatch means the canvas was built before a setting changed, or has hand edits.

Equivalence and the Baseline

The equivalence report compares the customer's own design (their Baseline) with the Product's.

  1. File > Baseline template (blank) or Baseline filled from this design saves AIDC-DBD-Baseline-v1.xlsx.
  2. File > Load Baseline… reads the filled Baseline (.xlsx or CSV key,value,unit,source), lists rows it cannot use, and opens the report.
  3. The report shows one row per metric: Baseline, Product, delta, within tolerance, class and reason. A class can be overridden with a reason.
  4. Download report saves <build>-equivalence.pdf and .csv; the status line gives each file's SHA-256.

Topology metrics must match exactly; counts are within tolerance when they differ by no more than 2%.

Reset and save

Reset starts a new design. It asks first: Save first, Reset or Cancel.

  • Cleared: every setting, the customer, code and build ID, Device IDs, Public IPs, tenants, site parameters, imported values, deviations you added, layout edits, the input sheet and Baseline records, and the saved copy in this window.
  • Kept: the tuned-profile library and the project folder.

Save the design before you Reset or close the app.

Tuned profiles

A tuned profile is the back-end lossless tuning measured on a site after it passed acceptance, exported by the Deployment Console for one switch model and OS release. Import it with Tuned profiles; later designs on the same switch model and release ship with the measured values instead of the starting defaults. A design can follow the library, pin one profile or use none.

A profile holds the switch model, OS, release, the numeric tuning values and a test summary, with a checksum. It holds no hostnames, addresses or counters. Reset keeps the library.

DC Layout Builder

The physical site: cabinets in rows and halls, the devices in each cabinet, and every cable run measured along the trays. The cable lengths in the Cable Matrix and the BoM come from here.

Opens from: the DC Layout button (Builder group) or Site build > DC Layout Builder, with the open build loaded. Past 512 racks it opens in its own window in large-site mode (see Large sites).

What it shows

ViewWhat it holds
Floor planHalls, rows and cabinets. The dashed outline around a group of rows is a data hall, sized by the Hall MW setting; it follows the rows when you move cabinets or change the floor columns.
ElevationsEach cabinet front, top to bottom: devices, cable managers and the patch field.

Settings that drive it

Set in the Fabric Designer, in the Layout settings strip: network cabinet height, row network, Floor columns (whole halls side by side; a site with three halls or fewer looks the same at 3 and 4 columns), keep pods in one column, AOC reach (a longer run becomes structured cabling), hall MW, feeds, compute power, row feed and FE+EDG footprint.

Working in it

  • Refresh from Fabric Designer takes the design as the Designer has it now and keeps your physical edits. Change a setting in the Designer, then refresh here.
  • Enter the site's real geometry (tray heights, aisle widths, room size). Until then, lengths come from default values and the Cable Matrix marks them indicative.
  • Save layout writes the cabinets, devices and your edits to the project folder. On a large site the file holds no links; they come from the design when the layout is opened again.

The deployment path

Each wave runs the steps in order, and each step's gate opens the next. In How to deploy this is stages 4 to 6:

  1. Step 0 cords laid, nothing energized.
  2. Step 1 OOB cabled → power on the OOB equipment → OOB gate. Only now power the rest of the wave; devices call in over their OOB drops and are claimed by ZTP.
  3. Step 2 Edge PoP cabled → software floor → start --plane edge → Edge gate.
  4. Step 3 front end cabled → start --plane fe → Front end gate (cabling check, MTU, BGP, DPU VTEPs, tenant isolation, ingress).
  5. Step 4 back end cabled (sheet 1, then 2 …) → start --plane be → Back end gate: lossless tests, then NCCL bus bandwidth at or above the target.

Crews can run ahead: step 3 or 4 can be cabled while the gate before it is being worked, as long as nothing is powered before its OOB drop is live.

Deployment Console

The provisioning host's web console. It brings the site up from the design: it serves DHCP and the zero-touch files, watches every device through its stages, pushes configurations, runs the gate checks and the acceptance tests, and ends with the hand-over.

Opens at: https://<prov IP>:8443, after the .run is installed and setup.sh has started the service (see How to deploy, stage 5). It runs on the provisioning host, not in the app.

Sign-in and logins

  • The admin password from setup.sh is temporary: change it at the first sign-in. New and reset passwords are temporary too.
  • Roles: admin (everything), operator (acts only on its planes: oob, edge, fe, be), viewer (read only). The Console warns when a plane has fewer than two people who can act on it.

Gates

When every device of a plane's last wave is Done (or quarantined), the plane goes to its gate. The gate runs its automatic checks (BGP, EVPN, cabling against LLDP, software release, lossless settings) and waits for the results that are entered.

Gate controlDoes

A passed gate backs up every device of that plane and lets the next plane start.

Tuning (back end)

Propose… new lossless values within their limits → Apply / roll back… to the test pod → run the tests again → Approve… → Roll out pod by pod (a smoke test per pod). Export profile… saves the approved values as a tuned profile for the Fabric Designer.

Backups

Every Done device is backed up after its build and then every 6 hours by default. Back up now, Diff vs planned and Diff vs previous are on each device.

Hand-over

  1. Take the final backup.
  2. The customer's admin clicks Download the hand-over export (as-built, SoT status, audit, events, readiness, tuning, the newest backup per device and apply_asbuilt.py) and checks its SHA-256; Confirm receipt… records it.
  3. Release DWR access… needs the receipt, two customer admins, four confirmations and the netadmin password. It removes the vendor account on every device, disables the vendor logins, locks the recorded host accounts and clears the push credential.

The CSV records are also at https://<prov IP>:8443/api/export/ (asbuilt, readiness, sot-status, audit, events). Then retire the host with sudo ./setup.sh --decommission.

How to deploy, start to finish

The whole path from the customer's inputs to handover, in seven stages. A step marked Gate must pass before you go on. Replace every <PLACEHOLDER> with the site's value.

1. Design freeze (workstation)

  1. Install the release frozen for this deployment (see Install and update) and check Help > About.
  2. File > New project folder… for this customer.
  3. File > Load input sheet… with the customer's filled sheet. Walk the import report with the customer and agree every "nearest supported" row as a design choice.
  4. If the customer has a Baseline: File > Load Baseline…, walk the equivalence report, agree or override each class with a reason, and Download report.
  5. Open Fabric health. Fix every Error; close, or get written acceptance for, every Open input.
  6. Optional, when the customer has sent serials or MACs: Device IDs, load the list (hostname,serial, hostname,MAC or serial,model). NVL72 racks: import the rack inventory (type,ru,bmc_mac,serial). Without a list, devices are bound as they call in (stage 5).
  7. Set the customer code and run Release check. Gate: Errors (0).
  8. Site build > Final package and .run (with the parity check). On another machine: Site build > Export site-runner file, then in the site runner folder: 
    node aidc-runner.js --html <builder>.html --design <site-runner>.json --out ./<SITE>
    To check again without rebuilding, add --parity-only. Gate: site-runner.log shows parity passed and no failed exports.
  9. Record the design fingerprint, plan digest and builder SHA-256 (all in site-runner.log) in the design register.

2. Procure

  1. Send the bill of materials (03-bill-of-materials) to the customer.
  2. Confirm every part number marked CONFIRM with the vendor before purchase orders go out.
  3. Order back-end spines and co-packaged-optics switches first, with delivery dates per wave.
  4. As units ship, collect serials and MACs for the Device IDs panel.

3. Site readiness

  1. Walk the floor plan and elevations against the room: cabinet positions, rows, clearances.
  2. Confirm each cabinet feed. For liquid-cooled (-LD) switches, confirm the 48 V DC busbar and the coolant flow (13.5 L/min per SN6800-LD, 5.7 L/min per SN6600-LD).
  3. Confirm fiber pathways, carrier circuits and cellular coverage for the console servers.
  4. Rehearse in DSX Air while hardware ships: Site build > Show DSX Air test files…, or by hand: 
    bash <SITE>-deploy-<VER>.run --extract-only --dir ~/t
cd ~/t/<SITE>-deploy
bash air/run-tests.sh
sudo bash air/ztp-host.sh [--engine go|python] [interface]
  5. Gate: the customer signs off site readiness for the first wave.

4. Install and cable (each wave)

  1. Give the crews the elevations, the Cable Matrix and the labels for the wave. Cable it step by step (see Cable Matrix: steps 0 to 4).
  2. Order: step 0 power cords (laid, not energized), step 1 OOB drops and console cables, then step 2 Edge PoP, step 3 front end and storage, step 4 back end.
  3. No device is powered before its OOB drop is live.

5. Provision (provisioning host)

  1. Copy the .run to the provisioning host on the OOB network and run it. It checks its SHA-256, unpacks to <SITE>-deploy/ and starts setup.sh: 
    sudo bash <SITE>-deploy-<VER>.run
  2. The first run copies secrets.env.template to /etc/fabric/secrets.env (mode 600) and stops. Fill every value: password hashes with openssl passwd -6; TARGET_BUSBW from the platform's all-reduce target.
  3. Run it again with the admin password and the first plane (bonded uplinks: add --bond NIC1,NIC2). It exits with code 4 while any placeholder is left: 
    sudo ./setup.sh --admin-pass '<P>' --plane oob
  4. Check the services: 
    sudo ./setup.sh --status
sudo journalctl -u estate-build -f
sudo journalctl -u kea-dhcp4-server -f     # RHEL: kea-dhcp4
  5. Open the Deployment Console at https://<prov IP>:8443. Change the admin password at first sign-in and enter the push credential. Add operator logins under Logins, or: 
    python3 /opt/estate-build/estate_build.py user add <NAME> --role operator --planes oob,edge
  6. Console servers: enroll each unit in Lighthouse, apply one Script template per unit from console/<NAME>.sh, and set SNMPv3 and syslog.
  7. Prove the OOB: a serial session to every port in console-ports.csv, one TACACS+ and one break-glass login, and one unit reached over cellular. Gate: the OOB gate passes in the Console.
  8. Power on the wave's devices; bind any under Unclaimed in the Console. Watch ZTP: Cumulus /var/log/ztp-<device>.log (sudo ztp -s); EOS show ip bgp summary; NX-OS show vpc.
  9. Software floor: 
    pip3 install netmiko
./os/check_os_release.py
    Gate: every device at or above its baseline.
  10. Start each plane in order (or Start build in the Console): 
    sudo python3 /opt/estate-build/estate_build.py start --plane edge
sudo python3 /opt/estate-build/estate_build.py start --plane fe
sudo python3 /opt/estate-build/estate_build.py start --plane be
  11. Junos devices pushed by hand: export FABRIC_USER=<user> FABRIC_PASSWORD=<pw>, then python3 push_configs.py --dry-run, then --plane mgmt, --plane fe, --plane be.
  12. Firewalls and ingress, where the design has them: python3 ftd_deploy.py --fmc <address> --dry-run, then without --dry-run; F5 BNK: kubectl apply of bnk/02-vlans, 03-bgp, 06-vxlan, 07-static-routes, 04-snatpools, 08-fw-policies, 05-gateways, in that order.
  13. Front-end DPUs: confirm DPU mode on every BlueField-3 (mlxconfig -d /dev/mst/mt41692_pciconf0 q INTERNAL_CPU_OFFLOAD_ENGINE must be 0); install with the Console's DPU runner or bfb-install; apply hbn/<host>-DPU.nvue in the DPU's HBN container with nv.

6. Validate (test pod first, then each wave)

  1. From acceptance/: python3 ../os/check_os_release.py, and the DPU-mode check on every host.
  2. Cabling: save each switch's LLDP table as lldp/<device>.csv, then python3 check_cabling.py. Gate: 0 mismatches.
  3. Optics for 15 minutes per link: no growing CRC or uncorrectable FEC errors, receive power in range.
  4. MTU: ping -M do -s 8972 <loopback> between leaf loopbacks; 9000-byte frames from each host's storage interface to a storage node.
  5. Control plane: every BGP session Established and every DPU VTEP reachable.
  6. Tenant isolation: CLIENT_SSH=<user>@<outside host> acceptance/ingress_isolation.sh.
  7. Lossless (test pod): HOSTFILE=pod<N>.hosts acceptance/lossless.sh T1, then T2, T3, T4; upload each result in the Console's back-end gate. T5 and T6 are run by hand. If a test fails, tune in the Console: Propose, Apply to the test pod, run again, Approve.
  8. NCCL: HOSTFILE=pod<N>.hosts TARGET_BUSBW=<GB/s> acceptance/nccl.sh, per rail then all rails; record it with estate_build.py result <BUSBW> <TARGET> or Enter result. Gate: bus bandwidth at or above the target.
  9. Storage: weka/03-checks.sh, then a read test from one host per pod, recorded as the baseline.
  10. Ingress: from outside, curl https://<VIP> for each tenant.
  11. After the test pod passes, roll the approved tuning out pod by pod, then repeat stages 4 to 6 for each wave.

7. Handover

  1. Export the records from https://<prov IP>:8443/api/export/: asbuilt.csv, readiness.csv, sot-status.csv, audit.csv, events.csv.
  2. Console > Hand-over (see Deployment Console), step 1: take the final backup.
  3. Step 2: the customer's admin downloads the hand-over export and checks its SHA-256 (sha256sum export.zip; Windows: Get-FileHash -Algorithm SHA256 export.zip).
  4. Optional, for the customer's source of truth: python3 apply_asbuilt.py netbox <URL> <TOKEN> --dry-run, then without --dry-run (or nautobot).
  5. The customer rotates every credential. Step 3: release vendor access (sudo ./setup.sh --release-vendor), and remove your Lighthouse login.
  6. Retire the provisioning host: sudo ./setup.sh --decommission. It writes the hand-over export first, asks you to type DECOMMISSION <SITE>, then removes the service, the DHCP configuration, the secrets and the served files.
  7. On your workstation, delete the customer's project folder, job folders and every customer-data/ folder. Gate: deletion record signed.
